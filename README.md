# csoul

A quiet little colorscheme studio for Neovim — first as a static terminal UI study.

This repository holds two things: a dependency-free Python script that paints
the finished picker with ANSI truecolor (`preview.py`, the design study), and the
Neovim plugin that implements it (`lua/csoul`, `plugin/csoul.lua`).

> **Note:** This project was entirely produced by generative AI. All code,
> documentation, and design decisions were generated by an AI coding agent
> under human direction.

## Run

The study is composed for **112 × 33 cells** and truecolor. The color chips
beside each scheme name use the Nerd Font glyph `󱓻` (`nf-md-square_rounded`),
so run it with a Nerd Font-patched terminal font.

```sh
python3 preview.py
```

Or, on this Nix machine:

```sh
nix run .
nix develop          # python3 + neovim + git
```

## Neovim plugin

`:Csoul` opens the picker as two floating windows. It needs Neovim 0.10 or
later (only 0.12.5 has been tested), `termguicolors`, and an editor of at least
122 × 38 cells.

| Key | Action |
| --- | --- |
| `j` / `k`, arrows | Move; only the picker's colours change, the editor keeps its scheme |
| `/` | Search by name (type, then `<Esc>` or `<CR>` to return to the list) |
| `<Tab>` / `<S-Tab>` | Cycle ALL / DARK / LIGHT |
| `<CR>` | Apply the selected scheme and close |
| `q` / `<Esc>` | Close without changing the scheme |

- Each scheme is loaded briefly to read its palette, then the editor's
  highlights, `vim.g` variables, and `runtimepath` are put back before anything
  is drawn, so the editor is not repainted while you browse and one scheme's
  state does not leak into the next.
- Schemes are measured in the background after the picker opens, a few at a
  time. Until a scheme is measured its LIGHT/DARK tag and the counts use a
  guess from the scheme file, and the header shows how many are left to
  measure. The counts and tags settle to what each scheme actually renders.
- Schemes come from the same places `:colorscheme` searches: `colors/*.vim` and
  `colors/*.lua` in `runtimepath`, and `pack/*/{start,opt}/*/colors` under
  `packpath`. Schemes that a plugin manager keeps outside those paths are not
  listed, because Neovim cannot apply them. When several files share a name,
  the first one `:colorscheme` would load is listed, and that same file is
  loaded for preview and apply.
- Before a scheme loads, its plugin directory is put first on `runtimepath`, and
  Lua modules that the scheme's plugin loaded during browsing are unloaded, so
  each preview matches a fresh `:colorscheme`. Modules that were already loaded
  when the picker opened are kept, as in a real apply.
- Palettes are read from the highlight groups after each scheme loads
  (`Normal`, `Function`, `Keyword`, `String`, …), so any installed scheme works
  without a table of colours.
- A scheme is LIGHT when its `Normal` background is light (relative luminance
  above 0.179, where black and white text have equal contrast). Schemes that
  leave `Normal` without a background use `background` to decide, and show black
  or white as the background.
- The syntax sample is a fixed Rust snippet. Each token takes its colour, weight,
  and italics from the scheme's own groups (`@keyword` → `Keyword` → `Statement`,
  and so on), falling back to the foreground colour when a group is missing.

Nix provides the plugin as `packages.<system>.nvim-plugin`, built with
`vimUtils.buildVimPlugin`:

```sh
nix build .#nvim-plugin
```

Flakes only read files tracked by Git, so `git add lua plugin` first, or use
`nix build path:.#nvim-plugin` while the files are still untracked.

## What it discovers

The script asks the local Neovim for its `runtimepath`, then scans:

- Neovim's own `runtime/colors`
- `~/.config/nvim/colors`
- lazy.nvim plugins (`~/.local/share/nvim/lazy/*/colors`)
- `pack/*/start/*` and `pack/*/opt/*`
- `plugged` and the usual XDG locations

It reports the real number of detected schemes, splits them into dark/light,
and shows where the selected scheme comes from (`nvim runtime`, a plugin, user
colors, or a curated fallback).

The static composition previews **Kanagawa Wave** when it is available, with a
curated fallback when it is not. The palette library in `preview.py` includes
the palettes used by the list; the active preview above uses Kanagawa Wave's
real highlight colours.

## Design notes

- Only elements that carry information or speed up choosing are drawn: search,
  filters, the scheme list with ten colour chips per row, key hints, the palette,
  a syntax sample, and UI chips (`Normal`, `Visual`, `Search`, `Error`, `Hint`).
- The selected row is a low-contrast wash with a solid accent spine.
- No frame, shadow, backdrop, gradients, dividers, or decorative letterspacing.
- Truecolor only; no third-party Python packages.
